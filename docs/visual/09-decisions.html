09 — Decisions

结论

Format per entry: ID, date, status (AGREED / PROPOSED / OPEN / IMPLEMENTED), context, decision, consequences. New decisions are appended; superseded ones are marked, never deleted.

1

Agreed by the owner (before this engagement)

RuleText
D-01AGREED — Independent portal integrated with Lab Care; a human decides which tickets are handovers.
D-02AGREED — Two identities: engineer (SSO) and recipient (detected on the device, confirmed by the engineer).
D-03AGREED — Snipe-IT writes should be attributed to the engineer; mechanism undecided (see D-12).
D-04AGREED — Database: PostgreSQL target (SQLite acceptable for development and tests).
D-05AGREED — Terminology follows Snipe-IT: checkout / checkin.
D-06AGREED — Paper signature stays; e-signature rejected by legal.
D-07AGREED — Git: never commit to feature/sso or main; one concern per branch.
D-08AGREED — Two dashboards eventually; this engagement delivers dashboard 1 (handovers).

Decisions made in this engagement

RuleText
D-09IMPLEMENTED — SQLAlchemy 2 async + Alembic; DATABASE_URL selects PostgreSQL (asyncpg) or SQLite (aiosqlite). Consequence: models restricted to portable types.
D-10SUPERSEDED — Ten fixed stages now include software_check after agent_report; skipped is satisfied for dependencies and completion; stored status is recomputed in one place.
D-11AGREED — The signed sheet is stored by the portal and pushed to the device's Snipe-IT asset (stage 9 depends only on stage 8). A missing recipient blocks stages 4 and 5 and makes the handover stalled, but never blocks the document.
D-12VERIFIED FACT; DESIGN OPEN — Snipe-IT v8.8.3 writes action_logs.created_by as the API token owner and sets action_source=api (live verification in docs/snipeit-api-verified.md). Current service-account writes therefore show the service account as actor; engineer email remains in the note and portal events. Whether to retain this mechanism or move to per-engineer credentials remains an owner decision (Q-13).
D-13AGREED — Document attach target is the device (asset), not the user. The exact endpoints are verified against the real Snipe-IT version in docs/snipeit-api-verified.md.
D-14OPEN — Stalled threshold by time, retention of events and documents, HTTPS rollout, agent single-use token binding.
D-15AGREED — H-Caliper is the owner's name for these 12 principle files; following H-Caliper means obeying and maintaining them.
D-16IMPLEMENTED — Graph file (03-graph-principles.md) is machine-checked by a test and updated in every branch that changes structure.
D-17IMPLEMENTED — One database session per request; app/dependencies.get_session is the only commit/rollback boundary. Repositories flush but never commit, so services compose calls inside one transaction.
D-18IMPLEMENTED — The engine and session factory are created lazily (app/db/engine.py); importing the app never opens a database connection, which keeps the characterization tests honest.
D-19IMPLEMENTED — The active-handover uniqueness rule is a partial unique index on handovers.device_serial with both postgresql_where and sqlite_where predicates, so SQLite tests enforce the same rule as production PostgreSQL.
D-20IMPLEMENTED — Domain errors are the only business-error vocabulary: routers translate HandoverNotFound → 404, invalid stage names → 422, and every workflow conflict (duplicate active serial, unmet dependency, non-manual stage, cancelled/completed) → 409. Services never import FastAPI.
D-21IMPLEMENTED — Stage 3 (agent_report) is evidence-driven: a report whose trimmed serial equals the handover serial passes it even when stage 1 is still pending; a missing or different serial fails it with a stored reason. This follows the Phase 2 instruction to "pass or fail stage 3" on submit, while every engineer-triggered action still goes through can_run.
D-22IMPLEMENTED — An agent session may optionally carry a handover_id. Without one, /api/session/new and /submit keep their pre-Phase-2 behavior and open no database connection. With one, the redacted report is stored and stage 3 is decided; an unknown, cancelled or completed handover never breaks the agent's submission contract.
D-23IMPLEMENTED — The Windows activation partial_key is removed from the agent payload before storage; the event trail stores only the reported serial and whether it matched, never the payload.
D-24IMPLEMENTED — recompute_status is the only writer of handovers.status. Cancellation calls it with cancelled=True, so an explicit cancellation can never be derived over by the stage rules.
D-25IMPLEMENTED — All Snipe-IT HTTP lives in app/clients/snipeit.py; routers, services and pages call typed client methods and never build a Snipe-IT URL, header or token themselves. The architecture test's LEGACY_HTTP_ROUTERS exemption is now empty.
D-26IMPLEMENTED — The client returns frozen dataclasses (SnipeItUser, SnipeItAsset, SnipeItFile, SnipeItActionResult) and raises four typed errors: SnipeItUnavailable, SnipeItAuthError, SnipeItNotFound, SnipeItRejected. Routers map them to 502/401-503/404/4xx-5xx; no raw httpx exception escapes the client.
D-27IMPLEMENTED — Retries are GET-only (two retries, small backoff) and cover network errors and HTTP 5xx. POST is never retried, because checkout, checkin and file upload are not guaranteed idempotent; Phase 5 verifies the resulting state instead.
D-28IMPLEMENTED — The bearer token is never logged and never included in an exception message. SnipeItAuthError carries only the HTTP status; tests assert the secret is absent from both str(exc) and captured logs.
D-29IMPLEMENTED — /api/snipeit/health now requires an authenticated user. It reports connected: false with a stable reason (token_not_configured, unreachable, api_error) instead of raising, so a monitoring caller can render status. No characterization test depended on public access.
D-30IMPLEMENTED — ServiceAccountProvider is the only credential provider in v1 (see D-12). The engineer's email is passed to the client for the Snipe-IT note and the event trail; the interface keeps a write flag so a future per-engineer provider can distinguish reads from writes.
D-31IMPLEMENTED — Local Snipe-IT v8.8.3 is bootstrapped repeatably by deploy/snipeit-dev/bootstrap.ps1 / .sh; live verification and endpoint shapes are recorded in docs/snipeit-api-verified.md.
D-32IMPLEMENTED — Recipient confirmation is an explicit engineer action. Search returns Snipe-IT candidates and flags the reported username when it matches the engineer's own identity (elevated-agent warning). Confirming a real user passes stage 4; choosing "not in Snipe-IT" (or confirming an id Snipe-IT does not know) stores the reason "Recipient not found in Snipe-IT", marks stage 4 blocked and stalls the handover. The portal never creates a Snipe-IT user.
D-33IMPLEMENTED — Stage 5 follows the mandatory idempotent algorithm: a passed stage makes no call; can_run guards dependencies; a missing serial fails with "Asset serial not found in Snipe-IT"; an asset already assigned to the confirmed recipient passes without a write; an asset assigned to anyone else fails without a write; otherwise the portal checks out, re-reads the asset and only passes when the assigned user id matches. A failed stage is retryable.
D-34IMPLEMENTED — Old-device checkin is not a workflow stage. It accepts only assets currently assigned to the confirmed recipient, refuses the handover device itself, treats an already-unassigned asset as done without a write, and reports every asset outcome in one response and one checkin_attempt event. Partial failures are never rolled back automatically.
D-35IMPLEMENTED — GET /api/handovers/{id}/preview is a dry run: it reads Snipe-IT and lists the checkout/checkin calls it would make, with warnings, and performs zero POSTs.
D-36IMPLEMENTED — Every Snipe-IT write attempt records an event with the outcome and, when available, the Snipe-IT HTTP status code. The checkout note always contains the engineer's email, "via Handover Portal", and the handover id, so attribution survives the service-account limitation (D-12).
D-37IMPLEMENTED — The printable report is server-rendered HTML from the latest stored, redacted agent report. It includes the handover id, hardware/software/activation evidence, and a signature block; it never reads windows_activation.partial_key and marks no stage. Printing is followed by the engineer confirming stage 6 by hand.
D-38IMPLEMENTED — Document acceptance is decided by magic bytes (%PDF-, PNG and JPEG signatures), never by the client filename or declared content type. DOCUMENT_MAX_BYTES is enforced while streaming; oversize is 413 and any other type is 415. The service stores a server-generated UUID filename under DOCUMENTS_DIR, records SHA-256 and keeps the sanitized client name for display only. The directory is never served statically.
D-39IMPLEMENTED — Download is authenticated and streams the latest stored document through FileResponse; a stored name that does not match the UUID pattern is rejected, so a tampered row cannot escape DOCUMENTS_DIR.
D-40SUPERSEDED BY D-61 — Stage 9's idempotent/verified pattern remains: a passed stage makes no call; a missing serial fails with "Asset serial not found in Snipe-IT"; a listed file matching the accepted filename rule passes without uploading; otherwise the portal uploads, re-lists the asset's files, and passes only when the file is visible. The recipient is not required, and the portal's copy is never deleted.
D-41IMPLEMENTED — Every document upload and push attempt writes an event (document_uploaded, document_push_attempt) with size, SHA-256, filename, outcome and Snipe-IT status code where applicable; no file bytes or tokens are logged.
D-42IMPLEMENTED — The dashboard is read-only and split in two: GET /api/dashboard/handovers/summary returns aggregates, and GET /api/dashboard/handovers returns one page of rows. No endpoint loads every handover; the summary is computed by SQL aggregates and the rows query is capped by page_size (max 100).
D-43IMPLEMENTED — Dashboard counts are dialect-portable: durations use julianday on SQLite and extract('epoch', ...) on PostgreSQL, selected by the session bind. Average time to complete is NULL until at least one handover has both timestamps.
D-44IMPLEMENTED — The summary zero-fills the fixed status and stage sets, so the response shape is stable when the table is empty and the UI never has to invent missing keys. "Top missing steps" only considers active cases (not completed or cancelled).
D-45IMPLEMENTED — /handovers and /handovers/{id} are server-rendered Jinja pages: the first paint already contains the real data, and the vanilla JS modules only refresh via the same JSON API. Every table has explicit loading, empty and populated states. All dynamic text goes through Jinja autoescape or textContent; no data reaches innerHTML.
D-46IMPLEMENTED — Page authentication mirrors the existing index rule: when SSO is enabled and the session has no user, both pages redirect to /login with the project's existing 307 RedirectResponse; when SSO is disabled they render the development user. The JSON endpoints keep returning 401 through current_user.
D-47IMPLEMENTED — The pages use external static/js/theme-init.js instead of an inline theme script so the Phase 8 self-only CSP can forbid inline script without a nonce; the only change to the legacy landing page is one "Start handover" link.
D-48IMPLEMENTED — The app fails closed: create_app raises when SSO_ENABLED=true and SESSION_SECRET is empty or the placeholder change-me. The development bypass (SSO_ENABLED=false) is exempt and keeps its loud warning.
D-49IMPLEMENTED — CSRF uses a per-session token generated with secrets.token_urlsafe(32), stored in the signed session and delivered in the X-CSRF-Token response header of GET /api/me. The JSON body of /api/me is unchanged so the characterization contract stays intact. State-changing requests under /api/handovers and /api/dashboard must echo the token; a present Origin must match the request host or APP_HOST. The agent submit endpoint is excluded because it has no cookie.
D-50IMPLEMENTED — CSRF enforcement applies when SSO is enabled. With SSO_ENABLED=false there is no authenticated session cookie to protect, so the development bypass skips the check; production always has SSO on.
D-51IMPLEMENTED — Security headers are attached to every response by a pure ASGI middleware: nosniff, same-origin referrer policy, DENY framing and a self-only CSP. To keep the policy strict, external Google Fonts were removed, the theme bootstrap moved to static/js/theme-init.js, the clipboard diagnostic script moved to static/js/diag_clipboard.js, and the printable report style moved to static/css/report.css. No unsafe-inline was added.
D-52IMPLEMENTED — Rate limiting is a dependency-free in-memory sliding window keyed by client address: 60 requests per 60 seconds for agent submit and for recipient search, configurable through RATE_LIMIT_*. It is single-process only; the limitation is Q-4.
D-53IMPLEMENTED — The secrets scan is a normal test over git ls-files: it fails on non-placeholder SNIPEIT_TOKEN, AZURE_CLIENT_SECRET or SESSION_SECRET assignments and on private-key headers. Placeholder values in .env.example are allowed.
D-54OPEN — The agent submit endpoint still trusts any holder of a valid short code. Single-use token binding is recorded as Q-3 and is not silently treated as solved.
D-55SUPERSEDED — Q-5 is resolved by the structured logging and request-ID implementation. Principle 02 now documents both the technical log path and append-only audit events.
D-56SUPERSEDED — pytest-cov and asyncpg were installed and prior coverage/PostgreSQL checks were measured under D-59; reruns after migration 0002 are part of this final verification.
D-57IMPLEMENTED (docs sync) — Principle files 06, 10 and 11 record the three deliberate deviations instead of hiding them: read-only dashboard aggregates live in the service (ARC-02), the duration aggregate is dialect-specific (TEC-05), and two files exceed the 400-line guide (CLN-02, Q-6).
D-58IMPLEMENTED (docs sync) — Principle file 12 reports the performance targets as unverified: no seed script or timing run exists yet (Q-7). README, the LIVE GRAPH and the tech-stack versions were brought in line with the code.
D-59MEASURED 2026-10-31 — pytest-cov 7.1.0 and asyncpg 0.32.0 install now, so the coverage and PostgreSQL claims in D-56/file 01 are measured for real: 94 % coverage on the default suite, and TEST_DATABASE_URL upgrade/downgrade/upgrade cycles pass on a real PostgreSQL 16 container (test_migration_runs_on_postgres passed instead of skipped). Skipped-remains-skipped never became passed without an environment.
D-60VERIFIED 2026-10-31 — Client/real API veracity fixes required by the live run: checkout payload key assigned_user (not assigned_to), hardware list filter needs assigned_to + assigned_type=App\Models\User, upload multipart field file[]. Implemented in app/clients/snipeit.py with the fake updated in tandem; shapes and evidence in docs/snipeit-api-verified.md.
D-61IMPLEMENTED (owner decision, 2026-10-31) — Snipe-IT v8.8.3 rewrites filenames to {item_id}-{random8}-{slug(original basename)}.{ext} and its file listing has no size field; the API token gets HTTP 403 from the asset-file download route. Stage 9 therefore matches the lowercased normalized original basename at the end of the stored filename, without byte-size comparison. The client maps a successful upload to its logical name within the same client instance; the service checks the stored suffix across later requests. This preserves retry idempotency but can collide when distinct scans share a basename. Q-8 records the accepted limitation.
D-62VERIFIED (2026-10-31) — Snipe-IT action_logs.created_by follows the API token owner. The service-account token therefore attributes the Snipe history to that account; engineer email remains in the note and portal event. See live evidence in docs/snipeit-api-verified.md.
D-63IMPLEMENTED — Recipient detection now captures user_domain and console_user, normalizes the SAM account name, blocks empty/local identities from auto-confirmation, and requires an explicit acknowledgement before confirming a detected identity that matches the engineer.
D-64IMPLEMENTED — Printable report contains the literal [Company legal text goes here] placeholder. No legal language is invented pending owner-provided approved text.
D-65IMPLEMENTED — app/domain/timeutil.py interprets naive SQLite datetime readbacks as UTC and normalizes aware values to UTC; status and duration calculations use UTC.
D-66PROPOSED — Inactive draft/in-progress handovers become stalled after STALL_HOURS (default 24; zero disables), computed in SQL for dashboard summaries/pages. The 24-hour policy remains open at Q-10.
D-67IMPLEMENTED — Structured key/value logging, request correlation via X-Request-ID, generic 500 responses, startup configuration summary and sanitized Snipe-IT call timing; no tokens, paths, identities or request bodies are logged. Q-5 is resolved.
