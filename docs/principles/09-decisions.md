# 09 — Decisions

Format per entry: ID, date, status (AGREED / PROPOSED / OPEN / IMPLEMENTED), context, decision, consequences. New decisions are appended; superseded ones are marked, never deleted.

## Agreed by the owner (before this engagement)
- D-01 AGREED — Independent portal integrated with Lab Care; a human decides which tickets are handovers.
- D-02 AGREED — Two identities: engineer (SSO) and recipient (detected on the device, confirmed by the engineer).
- D-03 AGREED — Snipe-IT writes should be attributed to the engineer; mechanism undecided (see D-12).
- D-04 AGREED — Database: PostgreSQL target (SQLite acceptable for development and tests).
- D-05 AGREED — Terminology follows Snipe-IT: checkout / checkin.
- D-06 AGREED — Paper signature stays; e-signature rejected by legal.
- D-07 AGREED — Git: never commit to `feature/sso` or `main`; one concern per branch.
- D-08 AGREED — Two dashboards eventually; this engagement delivers dashboard 1 (handovers).

## Decisions made in this engagement
- D-09 IMPLEMENTED — SQLAlchemy 2 async + Alembic; `DATABASE_URL` selects PostgreSQL (asyncpg) or SQLite (aiosqlite). Consequence: models restricted to portable types.
- D-10 IMPLEMENTED — Nine fixed stages derived from the owner's flow diagram; status derived by pure functions; stored status recomputed in one place.
- D-11 AGREED — The signed sheet is stored by the portal and pushed to the device's Snipe-IT asset (stage 9 depends only on stage 8). A missing recipient blocks stages 4 and 5 and makes the handover stalled, but never blocks the document.
- D-12 OPEN — Attribution mechanism for Snipe-IT writes. Interim: service-account token behind `SnipeItCredentialProvider`; engineer email written into the Snipe-IT note and the events table. Limitation: Snipe-IT history may show the service account as actor. Requires a test: personal token → checkout → read asset history.
- D-13 AGREED — Document attach target is the device (asset), not the user. The exact endpoints are verified against the real Snipe-IT version in `docs/snipeit-api-verified.md`.
- D-14 OPEN — Stalled threshold by time, retention of events and documents, HTTPS rollout, agent single-use token binding.
- D-15 AGREED — H-Caliper is the owner's name for these 12 principle files; following H-Caliper means obeying and maintaining them.
- D-16 IMPLEMENTED — Graph file (`03-graph-principles.md`) is machine-checked by a test and updated in every branch that changes structure.
- D-17 IMPLEMENTED — One database session per request; `app/dependencies.get_session` is the only commit/rollback boundary. Repositories flush but never commit, so services compose calls inside one transaction.
- D-18 IMPLEMENTED — The engine and session factory are created lazily (`app/db/engine.py`); importing the app never opens a database connection, which keeps the characterization tests honest.
- D-19 IMPLEMENTED — The active-handover uniqueness rule is a partial unique index on `handovers.device_serial` with both `postgresql_where` and `sqlite_where` predicates, so SQLite tests enforce the same rule as production PostgreSQL.
- D-20 IMPLEMENTED — Domain errors are the only business-error vocabulary: routers translate `HandoverNotFound` → 404, invalid stage names → 422, and every workflow conflict (duplicate active serial, unmet dependency, non-manual stage, cancelled/completed) → 409. Services never import FastAPI.
- D-21 IMPLEMENTED — Stage 3 (`agent_report`) is evidence-driven: a report whose trimmed serial equals the handover serial passes it even when stage 1 is still pending; a missing or different serial fails it with a stored reason. This follows the Phase 2 instruction to "pass or fail stage 3" on submit, while every engineer-triggered action still goes through `can_run`.
- D-22 IMPLEMENTED — An agent session may optionally carry a `handover_id`. Without one, `/api/session/new` and `/submit` keep their pre-Phase-2 behavior and open no database connection. With one, the redacted report is stored and stage 3 is decided; an unknown, cancelled or completed handover never breaks the agent's submission contract.
- D-23 IMPLEMENTED — The Windows activation `partial_key` is removed from the agent payload before storage; the event trail stores only the reported serial and whether it matched, never the payload.
- D-24 IMPLEMENTED — `recompute_status` is the only writer of `handovers.status`. Cancellation calls it with `cancelled=True`, so an explicit cancellation can never be derived over by the stage rules.
- D-25 IMPLEMENTED — All Snipe-IT HTTP lives in `app/clients/snipeit.py`; routers, services and pages call typed client methods and never build a Snipe-IT URL, header or token themselves. The architecture test's `LEGACY_HTTP_ROUTERS` exemption is now empty.
- D-26 IMPLEMENTED — The client returns frozen dataclasses (`SnipeItUser`, `SnipeItAsset`, `SnipeItFile`, `SnipeItActionResult`) and raises four typed errors: `SnipeItUnavailable`, `SnipeItAuthError`, `SnipeItNotFound`, `SnipeItRejected`. Routers map them to 502/401-503/404/4xx-5xx; no raw `httpx` exception escapes the client.
- D-27 IMPLEMENTED — Retries are GET-only (two retries, small backoff) and cover network errors and HTTP 5xx. POST is never retried, because checkout, checkin and file upload are not guaranteed idempotent; Phase 5 verifies the resulting state instead.
- D-28 IMPLEMENTED — The bearer token is never logged and never included in an exception message. `SnipeItAuthError` carries only the HTTP status; tests assert the secret is absent from both `str(exc)` and captured logs.
- D-29 IMPLEMENTED — `/api/snipeit/health` now requires an authenticated user. It reports `connected: false` with a stable `reason` (`token_not_configured`, `unreachable`, `api_error`) instead of raising, so a monitoring caller can render status. No characterization test depended on public access.
- D-30 IMPLEMENTED — `ServiceAccountProvider` is the only credential provider in v1 (see D-12). The engineer's email is passed to the client for the Snipe-IT note and the event trail; the interface keeps a `write` flag so a future per-engineer provider can distinguish reads from writes.
- D-31 IMPLEMENTED (live verification BLOCKED) — `deploy/snipeit-dev/` contains a development-only Snipe-IT v8 + MariaDB compose stack, a placeholder `.env.example` and exact setup steps. The stack could not be pulled here because Docker Hub requests time out in this environment; `docs/snipeit-api-verified.md` records the failure, the owner steps and the exact shapes still to verify. `tests/test_snipeit_live.py` is marked `live` and skipped unless `SNIPEIT_LIVE_TEST=1`; it only touches `TEST-` objects.
- D-32 IMPLEMENTED — Recipient confirmation is an explicit engineer action. Search returns Snipe-IT candidates and flags the reported username when it matches the engineer's own identity (elevated-agent warning). Confirming a real user passes stage 4; choosing "not in Snipe-IT" (or confirming an id Snipe-IT does not know) stores the reason "Recipient not found in Snipe-IT", marks stage 4 `blocked` and stalls the handover. The portal never creates a Snipe-IT user.
- D-33 IMPLEMENTED — Stage 5 follows the mandatory idempotent algorithm: a passed stage makes no call; `can_run` guards dependencies; a missing serial fails with "Asset serial not found in Snipe-IT"; an asset already assigned to the confirmed recipient passes without a write; an asset assigned to anyone else fails without a write; otherwise the portal checks out, re-reads the asset and only passes when the assigned user id matches. A failed stage is retryable.
- D-34 IMPLEMENTED — Old-device checkin is not one of the nine stages. It accepts only assets currently assigned to the confirmed recipient, refuses the handover device itself, treats an already-unassigned asset as done without a write, and reports every asset outcome in one response and one `checkin_attempt` event. Partial failures are never rolled back automatically.
- D-35 IMPLEMENTED — `GET /api/handovers/{id}/preview` is a dry run: it reads Snipe-IT and lists the checkout/checkin calls it would make, with warnings, and performs zero POSTs.
- D-36 IMPLEMENTED — Every Snipe-IT write attempt records an event with the outcome and, when available, the Snipe-IT HTTP status code. The checkout note always contains the engineer's email, "via Handover Portal", and the handover id, so attribution survives the service-account limitation (D-12).
- D-37 IMPLEMENTED — The printable report is server-rendered HTML from the latest stored, redacted agent report. It includes the handover id, hardware/software/activation evidence, and a signature block; it never reads `windows_activation.partial_key` and marks no stage. Printing is followed by the engineer confirming stage 6 by hand.
- D-38 IMPLEMENTED — Document acceptance is decided by magic bytes (`%PDF-`, PNG and JPEG signatures), never by the client filename or declared content type. `DOCUMENT_MAX_BYTES` is enforced while streaming; oversize is 413 and any other type is 415. The service stores a server-generated UUID filename under `DOCUMENTS_DIR`, records SHA-256 and keeps the sanitized client name for display only. The directory is never served statically.
- D-39 IMPLEMENTED — Download is authenticated and streams the latest stored document through `FileResponse`; a stored name that does not match the UUID pattern is rejected, so a tampered row cannot escape `DOCUMENTS_DIR`.
- D-40 IMPLEMENTED — Stage 9 uses the same idempotent/verified pattern as stage 5: a passed stage makes no call; a missing serial fails with "Asset serial not found in Snipe-IT"; a file already listed on the asset (matched by sanitized name and byte size) passes without uploading; otherwise the portal uploads, re-lists the asset's files, and passes only when the file is visible. The recipient is not required, and the portal's copy is never deleted.
- D-41 IMPLEMENTED — Every document upload and push attempt writes an event (`document_uploaded`, `document_push_attempt`) with size, SHA-256, filename, outcome and Snipe-IT status code where applicable; no file bytes or tokens are logged.
