## Q-1 — Does linking an agent session to a handover require ownership? (OPEN)

Context: `GET /api/session/new` accepts an optional `handover_id`, and the
unauthenticated agent later posts to `/api/session/{code}/submit`. The prompt
does not say whether the portal must verify that the handover exists and belongs
to the engineer who created the session code.

Conservative option taken: store the supplied id and let `/submit` ignore an
unknown, cancelled or completed handover; do not add a database lookup to
session creation. The session code is short-lived and random, and the engineer
chooses the id in the authenticated UI. If the owner wants stronger binding,
Phase 8 should validate existence and `engineer_email` at `/api/session/new`.

Owner: security owner.

## Q-2 — What does the `engineer` list filter match? (OPEN)

Context: `GET /api/handovers?engineer=` is specified as a filter but not as an
exact email, a name, or a substring search.

Conservative option taken: exact match on `engineer_email` (the identity the
portal records). A name/substring search can be added when the dashboard UI
defines its search box.

Owner: dashboard/UI owner.

## Q-3 — Should the agent short code be bound to a single use? (OPEN)

Context: `POST /api/session/{code}/submit` accepts any holder of a valid,
unexpired short code. The code is generated by the authenticated engineer and
typed into the agent script on the device. A code observed on the device (or in
a screenshot) can be replayed until it expires.

Conservative option taken: keep the current short TTL and rate limit the submit
endpoint (Phase 8). Do not add a new identity mechanism without the owner's
decision. A single-use token embedded in the generated script, or a
device-bound secret, would close the gap but changes the agent contract.

Owner: security owner.

## Q-4 — Where should rate-limit counters live when the app runs multi-worker? (OPEN)

Context: the Phase 8 limiter is in memory and therefore per process. Two
workers behind a load balancer each allow the configured number of requests.

Conservative option taken: document the limitation and keep the limiter for
the single-process deployment used today. A shared store (Redis, or a small
database table) is needed before horizontal scaling.

Owner: platform/operations owner.

## Q-5 — Should structured technical logging and request ids be added? (OPEN)

Context: principle file 02 describes structured `key=value` logs, a request id
returned as `X-Request-ID`, level policy and a startup configuration summary.
None of that is implemented: the app relies on uvicorn's default logging and
the `events` table for the audit trail.

Conservative option taken: do not claim the logging stack exists; keep the
token/secret logging prohibitions and the append-only event trail. The final
sync rewrites file 02 to separate implemented audit behavior from the
unimplemented technical logging.

Owner: platform/operations owner.

## Q-6 — When should the two oversized files be split? (OPEN)

Context: principle 11 asks for files ≤ 400 lines. At final sync
`app/services/snipeit_ops.py` is 640 lines and `static/js/handover_detail.js`
is 461 lines. Both are cohesive, and splitting them now would mix refactoring
with the documentation sync.

Conservative option taken: record the exception in file 11 and defer the split
to a dedicated `refactor/` branch with its own tests.

Owner: code owner.
